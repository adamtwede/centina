# AISL Tooling Roadmap

Tracks the implementation of the AISL checker/tooling, as distinct from `PLAN.md`
(which tracks the AISL *language spec* itself, via the not-yet-written
`SPEC.md`/`ARCHITECTURE.md`). See `RUNLOG.md`-style usage if this grows long —
for now, current state lives here directly.

## Done

- Indentation-aware lexer (`src/lexer.ts`)
- AST definitions (`src/ast.ts`)
- Recursive-descent parser (`src/parser.ts`)
- Checker v0 (`src/checker.ts`):
  - scope/identifier resolution
  - nominal type checking on annotated params/vars/returns, `Unspecified` as the gradual-typing escape hatch
  - exhaustive `match`/`case` checking over declared enums (no catch-all `else`)
  - `Agent.prompt()`/`.review()` always type as `Unspecified`; using the result as another type requires an explicit `as` cast
  - `@agent:`-tagged comment-only function bodies are treated as intentional stubs, not flagged
  - undeclared dot-notation property access (e.g. `target_model.specification`) is unchecked by design
- CLI (`src/cli.ts`, `npm run check <file>`)
- Validated against `prototype.aisl`: surfaces exactly one real diagnostic (see below), no false positives

Also done:

- **Interactive iteration loop** — `aisl-iterate` project skill (`.claude/skills/aisl-iterate/SKILL.md`) encoding: run checker -> triage each diagnostic as mechanical-fix-it or genuine-ambiguity-ask-the-human -> apply agreed fix -> re-run -> repeat until clean. Chosen over a CLAUDE.md instruction or a hypothetical harness "mode" (not a real extension point in this tool).
- First real use of the loop: `prototype.aisl:50`'s `Step`/`String` mismatch in `escalate()` resolved by threading `implementation_step` through `escalate`'s signature so re-escalation re-enters `implementation_loop` with the abstract step (letting it regenerate a prompt tailored to the escalation model's `specification`), rather than retrying the original target's pre-rendered prompt verbatim. `prototype.aisl` now passes the checker with zero diagnostics.

Also done:

- **Test fixtures** (`tests/`, run via `npm test`) — `node:test` + `tsx`, zero extra dependencies. `lexer.test.ts`, `parser.test.ts`, `checker.test.ts` (17 cases covering scope errors, nominal mismatches, enum exhaustiveness, the `Unspecified`/cast rule, stub bodies, arg-count/unknown-type errors), and `prototype.test.ts` as a standing regression fixture asserting `prototype.aisl` stays at zero diagnostics.
- Writing the `Unspecified`/cast tests caught a real bug: `tyEquals` was symmetric, so an uncast `Agent.prompt()`/`.review()` result was silently accepted anywhere — defeating the whole point of the cast rule. Fixed by replacing it with a directional `isAssignable(expected, actual)`: `Unspecified` is accepted wherever a concrete type is expected only via going the other way (concrete -> `Unspecified` slot is fine; `Unspecified` -> concrete slot requires an explicit `as` cast).

Also done:

- **VSCode syntax highlighting** (`editors/vscode/`) — minimal, unpublished extension: `package.json` registers the `.aisl` language, `language-configuration.json` covers comments/brackets/auto-indent-after-`:`, `syntaxes/aisl.tmLanguage.json` is a heuristic TextMate grammar (keywords, builtin types, `@agent:` comments highlighted distinctly from plain comments, ALL_CAPS-as-enum-member and PascalCase-as-type-name heuristics, decl-name capture for `function`/`enum`/`type`). To use: open `editors/vscode/` as a folder in VS Code and press F5 to launch an Extension Development Host with it active — nothing to publish or package for local dev.
- **VSCode inline diagnostics** (`.vscode/tasks.json`) — a "AISL: Check current file" task that shells out to the existing `aisl-check` CLI (`tsx src/cli.ts`) and a problemMatcher regex (`^(.*):(\d+):\s+(error|warning):\s+(.*)$`) that maps its output straight into the Problems panel. Per-save/per-task-run, not live-as-you-type — deliberately the cheap option, see below.

Also done:

- **String templating** — backtick-delimited template strings (`` `text ${expr} more` ``), added across the full stack: lexer (`TEMPLATE_STRING` token, segment-splitting on `${...}` with brace-depth tracking), AST (`TemplateStr` expr node with `TemplatePart[]`), parser (each `${...}` raw segment is re-tokenized/re-parsed as a standalone expression via a nested `Parser` instance, with token line numbers patched to the original source line), checker (`TemplateStr` always types as `String`; each embedded expression is still checked for undefined identifiers etc., same as any other expression), and the VSCode grammar (backtick strings get their own `string.template.aisl` scope, with `${...}` bodies highlighted via a self-recursive embedded-language region so expressions inside get full AISL highlighting, not just plain string color). `prototype.aisl`'s five `+`-concatenation call sites were converted to templates as the worked example; `+` itself is untouched (still used for non-string-building contexts, and the checker still doesn't special-case it) — whether to add a structural warning nudging future `+`-on-strings usage toward templates is open, see backlog.
- **`@agent:` highlighting fix** — `@agent:` comments were already a separate TextMate scope, but most themes don't visually distinguish "doc comment" from "comment," so it rendered identically to a plain `#` comment in practice. Fixed by giving just the `@agent:` marker itself a `keyword.other.prompt.aisl` scope (reliably colored across themes) via a `begin`/`beginCaptures` rule, while the rest of the line stays scoped as a normal line comment.

Also done:

- **Warning-level structural checks, first batch** (`src/checker.ts`):
  - **Property access on `Unspecified` warns** — `.prop` access on a value whose own type is `Unspecified` (an uncast `Agent.prompt()`/`.review()` result, or an `Unspecified`-typed binding) now warns, since it's an unproven assumption about a shape nothing has committed to yet. Deliberately *not* re-flagged on chained access (`a.spec.nested`) — property access always types as `Unspecified` by design (properties stay dynamic), so only the first dot off a non-Member expression is checked; otherwise every legitimate chained property access would falsely trip the same warning.
  - **Property-name typo detection** — collects every `obj.prop` access where `obj`'s type is a known named type into a `typeName -> propName -> lines[]` map, then flags spellings that are close (Levenshtein distance, scaled by name length) to a *strictly more common* spelling on the same type as a likely typo. Equally-common spellings are left alone — that's a genuine naming inconsistency for a human to resolve, not something the checker can pick a side on.
  - Still open from the original candidate list: dead code after `return`, functions declared but never called, params declared but never used.

Also done:

- **External symbol references, unified across real code and other local `.aisl` files** — one syntax, `external (type|function|object) Name from "path"`, or with a renamed real symbol, `external renamed (type|function|object) Name from "path" was RealName`, e.g. `external type Step from "src/models.ts"` or `external type Step from "shared.aisl"`. There's no separate `import` keyword — resolution branches internally on the target path's extension, but the AISL author always writes the same statement shape regardless of what's on the other end. (Syntax notes: `from` replaced an earlier `=` to read less like an assignment; the `renamed`/`was` clause keeps the AISL-facing alias in the same position relative to the source path whether or not it's renamed, rather than a trailing bare name that read like an assignment target; `type`/`function`/`object` stay explicit kind keywords — collapsing them into one generic `symbol` keyword, or omitting the kind entirely, were both considered and rejected, since the kind cross-check against the real file is worth keeping in both cases.)
  - **Real code or a bare library specifier** (`src/resolveExternals.ts`, runs *after* `check()`) — the symbol always types as `Unknown` (distinct from `Unspecified`: same must-cast-before-flowing-into-a-concrete-slot rule, but member/method access on `Unknown` is never flagged, while every cast *off* `Unknown` warns about the unverified assumption). Verification is regex-based, not a real parser, and only covers ECMAScript and Python; bare library specifiers (`"lodash"`, `"numpy"`) are never resolved at all. Every miss is a warning, never an error, since the heuristic can't see re-exports/barrel files/decorators.
  - **Another local `.aisl` file** (`src/resolveLocalExternals.ts`, runs *before* `check()`, since the checker needs the real declaration's shape synchronously) — the symbol is treated exactly as though declared natively in this document: real nominal typing, never `Unknown`, because the target can be parsed and checked directly. Finds the requested name among the target's own declarations across every namespace (enum/type/function/global/external), clones it under the alias, and splices the clone into the importing program before `check()` runs (results cached per absolute path, so a file referenced several times is only parsed/checked once). If the declared kind keyword doesn't match what the target actually declares, that's a warning, but resolution still proceeds using the *real* discovered kind, so usage isn't broken just because the label was wrong.
    - **Errors (not warnings) on**: the target file having its own checker errors (`"errors in '<file>' must be resolved before symbols can be referenced"`); the requested name resolving only via *another* `external` entry in the target file — a forwarding chain — rather than a real declaration (`"'<name>' is itself declared as external... reference it directly"`, refusing to chase the chain); the alias colliding with anything already declared locally or with another external's alias in the same file.
    - **Deliberately single-hop, never transitive**: resolution never recurses past the one file directly named in the `external` statement. Side effect: no real cycle-detection machinery is needed, since a chain longer than one hop can't form — `A` referencing `B` referencing `A` just fails fast with the forwarding-chain error the moment a second hop would be needed.
    - **Missing-dependency-type detection, not auto-resolution** — only the requested declaration itself is cloned, so a referenced function's signature (or a referenced global's type annotation) naming another custom type that isn't itself separately imported used to silently surface as a confusing `unknown type 'X'` at the *call site*, not the `external` line. Now detected up front, before injection: every named type in the signature is checked against everything that will be available (builtins, this document's own native decls, and every other `.aisl` external's alias requested here, regardless of file order), and a single error at the `external` line lists the exact `external type X from "path"` line(s) needed — copy-paste fixable. The dependent symbol is deliberately *not* injected when this fires, so downstream "is not a defined function"/"unknown type" diagnostics at call sites are expected secondary fallout pointing back at the one real error, not bugs to suppress. Chosen over transitively auto-importing the dependency: that would reopen the cycle-detection problem the single-hop design exists to avoid, plus raise an unresolved question about which name a transitively-pulled type should get under a `renamed`/`was` import.
    - A cloned `external` entry whose own target is a local real-code path gets that path rebased to an absolute path anchored at the file it was found in (not the importer), so a later `resolveExternals` pass run from the importing file's directory still finds the right file.

Also done:

- **Operating principle: AISL never manufactures data** — every concrete value in a document has to trace back to one of a small set of privileged sources: a function parameter, `Agent.prompt()`/`.review()` (or any future privileged built-in built the same way), or an `external` reference. All future language/checker proposals get checked against this before being designed further. Considered and rejected as a result: a `new Type` construction for "conjuring" an opaque instance of a custom type — custom types have no construction logic anywhere in an AISL document (unlike `Agent(...)`, which invokes the tool's own privileged primitive, not a domain object), so there's no legitimate fifth source for it to represent; the honest way to say "I need a new Step" is whichever real source actually produces it.
  - **Closed a loophole this exposed** (`src/checker.ts`) — calling an undeclared method on *any* object (a custom type, `Agent` itself outside `.prompt()`/`.review()`, an `Unspecified`-typed value) already typed its result as `Unspecified`, which is castable by design — making any ad-hoc method call a backdoor `Agent.prompt()`-equivalent able to "produce" data of any concrete type without going through a privileged path. Fixed with a dedicated fourth `Ty` kind, `Unprivileged`, rather than a boolean flag on `Unspecified` — a flag would make the restriction opt-in (every existing `kind === "unspecified"` check would silently keep treating it as castable unless someone remembered to also check the flag), whereas a separate `kind` makes it opt-in the other way: anywhere `"unprivileged"` isn't explicitly handled, it falls through to a type mismatch (rejected) rather than being silently accepted. `Unprivileged` behaves like `Unspecified` for descriptive use (chaining, passing as an argument, bare statement calls — all still unflagged, and still useful as a discoverability/documentation source, see Backlog), but casting or assigning it into a concrete type is a checker **error**, not a warning. A method call on an external (`Unknown`-typed) receiver is unaffected — `external` stays its own privileged source, with the existing warn-only cast rule.
  - **Known limitation, not yet solved**: the non-privileged flavor doesn't survive across a user-defined function boundary — a function with no declared return type that forwards an ad-hoc call's result reports the function's own (privileged, castable) `Unspecified` signature type to its callers, so wrapping the violation in an indirection still bypasses the check. Closing this fully would need real return-type inference from a function's body, not just trusting its declared signature; not attempted yet since the immediate case (no indirection) was what prompted this.

Also done:

- **`test.aisl` worked example + the checker fixes it surfaced** — a second standing fixture (alongside `prototype.aisl`) whose comments assert what should/shouldn't be allowed, exercising the `Unspecified`/`Unknown`/`Unprivileged`/`Agent` interactions specifically. Authoring it exposed (and this session fixed) a batch of holes in the checker; each fix has test coverage in `tests/checker.test.ts`:
  - **Mixed tabs/spaces was the "inconsistent indentation" report, not a lexer bug** — the file mixed tab- and space-indented body lines; the lexer's deliberate Python-style prefix comparison (`src/lexer.ts`) correctly rejected it. Normalized the file to spaces; no toolchain change. (A formal-grammar rewrite was considered per the human's prompt and judged unnecessary — every real defect was in checker *type rules*, not lexing/parsing.)
  - **All four owned type names are now reserved** (`Agent`, `Unspecified`, `Unknown`, `Unprivileged`) via a `BUILTIN_TYPE_NAMES` set — `type X` on any of them errors with "cannot redefine built-in type 'X'" (distinct from the duplicate-user-type "already declared" message). Previously only `Agent`/`Unspecified`/`Unknown` were caught (incidentally, via `isKnownTypeName`); `Unprivileged` slipped through entirely.
  - **`Unprivileged` can never be written in source** — `resolveTypeRef` rejects it as an annotation, return type, or cast target with one error, then recovers as `Unspecified` to avoid a cascading second diagnostic on the same construct. This implements the human's proposed rule ("Unprivileged should not be usable as a function return type") and generalizes it to every written position. A `-> Unprivileged` function is therefore flagged at its *signature*; its body return is then checked against the recovered `Unspecified` (so e.g. `return some_concrete_value` in such a function does not double-report).
  - **An `Unprivileged` value may not be stored or returned** — binding an ad-hoc method-call result to a variable/global (`x = s.whatever()`) or returning it now produces a dedicated, clearly-worded error (`rejectsUnprivilegedBinding`) instead of the old nonsensical self-mismatch (`expected 'Unprivileged', got 'Unprivileged'`), which arose because an un-annotated binding copied the init type and then compared it to itself. It stays usable descriptively (chained, called again, passed where `Unspecified` is expected).
  - **Cast rule restrictions** (`checkExpr` `Cast` case), all hard errors per the human's "fail closed" preference: (a) casting *off* an `Unprivileged` value to **anything** — previously only `named`/`array` targets were caught, so `as Unspecified`/`as Unknown` was a laundering escape; (b) casting *to* the privileged built-in `Agent` (no constructor-free way to make a working Agent); (c) casting directly between `Unspecified` and `Unknown` (distinct escape hatches, not interchangeable).
  - **`Agent.prompt()` static form deferred, not adopted** — `test.aisl` originally wrote `Agent.prompt(...)` (capital, static-style); the human confirmed the instance form (`agent.prompt(...)` on an `Agent`-typed value, as in `prototype.aisl`) is the only privileged path, so the fixture was corrected rather than the checker extended.

Also done:

- **`tests/fixtures/broken2.aisl`** — a regression fixture for two false non-errors in `isAssignable` (`src/checker.ts`): the expected-side short-circuit (`expected.kind === "unspecified" || "unknown" → return true`) accepted *any* actual type, so an external (`Unknown`) value returned from a `-> Unspecified` function, and a concrete/`Unspecified` value returned from a `-> Unknown` function, both passed silently — even though the Cast rule already treats `Unspecified`/`Unknown` as non-interchangeable. Fixed by making `isAssignable` enforce that distinction for assignment/return too: `Unspecified` accepts concrete or `Unspecified` (not `Unknown`); `Unknown` accepts only `Unknown` (its sole legitimate source is an `external` reference). Surfaced a knock-on false positive: an *un-annotated* function defaults its return type to `Unspecified`, and the stricter check then wrongly flagged it for returning an `Unknown` param. Fixed by tracking `FunctionSig.returnAnnotated` and only enforcing the return-type check when the author wrote an explicit `-> T` — a defaulted `Unspecified` makes no claim to check against. Covered by 6 new `checker.test.ts` cases plus the fixture.
- **Missing-dependency-type error for `.aisl` externals** (`src/resolveLocalExternals.ts`) — see the entry under external symbol references above; exported `BUILTIN_TYPE_NAMES` from `checker.ts` so the resolver can compute "type names available in the importer" without duplicating the builtin list.

Also done:

- **Cast warning for unrelated concrete `named` types** (`checkExpr` `Cast` case, `src/checker.ts`) — closes backlog item 98(2): casting between two concrete nominal types with no subtyping relationship (e.g. `Agent(...) as Step`, or one custom type as another) now warns, rather than passing silently. Implemented generally on any `named`→`named` cast where the names differ, rather than special-casing `Agent`, so it also catches the built-in-to-custom and built-in-to-built-in cases `broken2.aisl` flagged (`Agent` as a custom type, `Agent` as `String`). Kept a warning, not an error, per the existing backlog reasoning: rare legitimate "treat this opaque blob as a different opaque blob" cases exist. Confirmed by design (not a bug) and left alone: casting a concrete type back into a `-> Unspecified` function's return slot, since `Unspecified` is deliberately the leaky escape hatch (vs. `Unknown`, which is strict) — tightening that would blur the distinction the two types exist to draw.
- **Lexer: comment-only lines no longer phantom-open a block without a real opener** (`src/lexer.ts`) — found via `broken2.aisl`: toggling a function header's line-comment and its body's line-comment *separately* (rather than together) left the body comment at its original deeper indentation with no real colon-terminated line preceding it, so the lexer still pushed an `INDENT`/`DEDENT` pair the parser never expected at the top level (`unexpected token '\t' at top level`). Toggling both lines together didn't trigger it, since then neither line claims any indentation at all. Fixed by tracking whether the immediately preceding line actually ended with `COLON`; a comment-only line indented deeper than the current block without that no longer pushes the indent stack, instead staying at the current level — while the legitimate `# @agent: ...`-as-sole-function-body case (which does follow a real colon-terminated header) is unaffected. Regression test in `tests/lexer.test.ts`; `prototype.aisl` re-verified at zero diagnostics.

Also done:

- **Fit-determination loop** — `aisl-fit` project skill (`.claude/skills/aisl-fit/SKILL.md`), the phase *before* `aisl-iterate`: it answers "should this be an AISL spec at all, and where do I slice it?" rather than refining one that already exists. Encodes the **structural/realization** two-plane model (AISL owns provenance/flow/contract; it recuses from algorithm/dynamics/aesthetics — the same split as "never manufactures data," seen from two sides), the **boundary-end count (2/1/0)** heuristic, and a three-level **descent** (prose inventory → signatures-only → thin slice) where the human stops at the highest level that draws the line and the agent supplies *form, never meaning* (skeletons with holes; the human fills the nouns/shapes/directions). A conclusive session emits a `specs/<name>/FIT.md` handoff that `aisl-iterate` consumes — establishing the per-feature lineage **FIT.md → `<name>.aisl` → PLAN.md**. Includes a precedent corpus (`precedents/`, canonical pool shipped with AISL + a project pool in the user's repo) matched as priors-not-verdicts, with a false-positive **edge-edit revision loop** that sharpens the matcher's discriminators over time. The compute-shaped-vs-I/O-shaped finding that motivated all of this is recorded in `docs/boundaries.md` ("When *not* to reach for a boundary").

## Next up

- **Boundaries** — first-class user-declared privileged data sources/sinks (`datasource`/`datasink`/`boundary`), the generalization of `Agent` to author-defined data seams, intended to make AISL a robust medium beyond the agent-supervisor domain (web apps, CLIs, servers). **Designed, not yet implemented** — full decisions, syntax, type rules, and the affordances-not-transports modeling guidelines live in `docs/boundaries.md` (the first concrete fragment of the eventual `SPEC.md`). Checker/parser work not started. The first feature spec targeting this work is `specs/add_boundary_primitives/` (with a worked `FIT.md` from `aisl-fit`).

## Deferred

- **Language Server (LSP)** for live-as-you-type diagnostics, wrapping the existing checker. Not started — the Problem Matcher task covers diagnostics cheaply for now, and the language's syntax/type rules are still changing session-to-session; an LSP is a bigger investment better spent once that settles down.

## Backlog / not yet scheduled

- `prototype.aisl` still has more to iterate on (per the human) beyond the one resolved mismatch — revisit with `aisl-iterate` in a future session.
- Possible structural warning: flag `+` used to concatenate two `String`-typed operands, nudging toward template strings instead. Not designed yet — would need to decide whether it only fires when both sides are *known* String (vs. Unspecified, where `+` could mean something else entirely).
- Type declaration syntax — under discussion; types currently declare a name only with fully dynamic, unchecked properties by design, to keep an AISL document feeling like a structured conversation rather than a prescriptive schema. Considered and rejected: (1) optional property lists with zero enforcement (too easy to mistake for real enforcement), (2) opt-in per-type `strict` enforcement (still schema-shaped, in tension with the "conversation, not contract" framing). Current direction: no new declaration syntax — the typo-detection check above and usage-based autocompletion (next item) are meant to deliver most of the same ambiguity-reduction value without introducing a schema.
- **IDE autocompletion on type properties** (deferred, not started) — usage-based rather than declaration-based: scan the document for all `x.prop` accesses on variables of a given type (the same `propertyUsage` map the typo check already builds) and offer those as completions, rather than requiring properties to be declared up front. Bigger lift than the typo check since it needs to run live in the editor (a `CompletionItemProvider` in the VSCode extension, shelling out to re-run analysis on keystroke) rather than once at check-time — no LSP required, but more than the current Problem Matcher task does today.
- **Full module resolution for library specifiers** (deferred) — resolving `external` declarations that point at installed packages (`node_modules`, Python `site-packages`) rather than local files would need real module resolution and `.d.ts`/stub parsing — a "fully dedicated linker/resolver," not a regex heuristic. Bare specifiers stay permanently unverified (single warning) until this is built, if ever justified by actual need.
- **Transitive type-dependency resolution for `.aisl`-targeted externals** — **resolved, by rejecting auto-import in favor of a clear error** (see "Also done" above): a missing dependency type is now reported as a single error at the `external` line with copy-pasteable fix lines, rather than silently leaving the type unresolved at the call site. Real transitive auto-pulling remains undone and is not currently planned, since the error path covers the need without reopening cycle-detection/renamed-import questions.
- **Usage-derived "what's available" artifact** (under discussion, not started) — a generated, descriptive-not-prescriptive reference table per AISL document: document-scope functions, plus per-type entries (function and non-function properties alike) derived from usage, including symbols pulled in via `external`. Built-in privileged types (`Agent`, and any future ones) get hand-seeded entries with their real constructor/method signatures, since there's nothing in an AISL document to scrape them from. The intended payoff is answering "why can't I do this with my own type" structurally rather than via prior documentation knowledge: a built-in shows a real constructor signature; a custom type shows none, plus wherever its values actually entered the document (which params take it, which casts produce it, which externals return it). Ad-hoc method calls on custom types should still appear (spec-writer aid), but clearly marked unprivileged/non-castable per the "AISL never manufactures data" principle above. Regenerated wholesale on save or check-run, never hand-edited. Open question carried over from the type-declaration discussion above: what (if anything) this needs to support real autocompletion vs. just being a reference doc.
- **Cast restrictions to round out the data-manufacturing principle**: (1) any cast to a privileged built-in type (e.g. `x as Agent`) should be a checker **error** — **DONE** (see "Done" above), along with the related `Unspecified`↔`Unknown` non-interchangeability error and the broadened cast-off-`Unprivileged` error. (2) a cast between two already-concrete nominal types (e.g. `x as Feedback` where `x` is already a `Step`, or a built-in like `Agent` cast to a custom type) should be a **warning** — **DONE** (see "Also done" above).
